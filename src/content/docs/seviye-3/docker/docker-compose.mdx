## Tek container yeterli değil

Gerçek sistemler birden çok parçadan oluşur: uygulama + veritabanı + cache + monitoring. Bunları elle `docker run` komutlarıyla ayağa kaldırmak (doğru sıra, doğru ağ, doğru flag'ler...) hataya açık bir manevradır. **Compose**, bu tanımları YAML'a yazmanı sağlar:

```bash
docker compose up -d      # TANIMLANDIĞI GİBİ her şey ayağa kalkar
docker compose down       # hepsi kapanır
```

## compose dosyası

`docker-compose.yml`:

```yaml
services:
  site:
    build: .                       # Dockerfile'dan kur
    ports:
      - "8080:80"                  # host:container
    restart: unless-stopped

  prometheus:                      # Seviye 4'ün kahramanı — şimdiden tanıyalım
    image: prom/prometheus:latest
    ports:
      - "9090:9090"
    volumes:
      - ./monitoring/prometheus.yml:/etc/prometheus/prometheus.yml:ro

  grafana:
    image: grafana/grafana:latest
    ports:
      - "3000:3000"
    depends_on:
      - prometheus
```

Artık `docker compose up` ile: site 8080'de, Grafana 3000'de, Prometheus 9090'da — **tek komut**.

## Container network: servis adı = hostname

Compose otomatik bir ağ yaratır; içinde **servis adı DNS adıdır**:

```yaml
# prometheus.yml içinde site'ı şöyle adreslersin:
targets: ["site:80"]     # IP değil, servis adı!
```

Container'lar birbirine servis adıyla ulaşır — Kubernetes'teki service DNS'inin (bir sonraki modül) yerel provasıdır.

## Volume: veri container'ın ölümünden uzun yaşamalı

Container silinince **yazım katmanı da silinir** (Seviye 3 dersi 1). Veriyi kurtarmak için volume:

```yaml
volumes:
  - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro   # bind mount: dosya bağla
  - prom-data:/prometheus                                 # adlandırılmış volume
volumes:
  prom-data:
```

- **Bind mount:** host'taki klasör/dosyayı container'a bağla — geliştirmede kod senkronu için
- **Named volume:** Docker'ın yönettiği depo — veritabanı verisi için

<Callout type="info" title="Gerçek dünyadan: dev containers — compose fikrinin standardı">
  GitHub Codespaces ve **devcontainer.json** standardı, compose'un çözdüğü
  problemi (“makinede çalışıyor” değil, “tanımda tanımlı çalışıyor”) bulut
  geliştirme ortamlarına taşıdı: ekip, geliştirme ortamını bir dosyada
  versiyonlar; yeni üye ilk günde üretken olur. Compose'u bugün öğrenmek, bu
  standartları yarın okumaktır — kavram birebir aynıdır.
</Callout>

## Compose'un DevOps'taki yeri

- **Lokal geliştirme:** “readme'ye göre 7 komut çalıştır” yerine `docker compose up` — yeni ekip üyesi ilk günde üretken olur (developer experience!)
- **CI'da entegrasyon testleri:** test job'ı `docker compose up -d db` ile gerçek veritabanına karşı koşar
- **Kubernetes'e geçiş köprüsü:** compose YAML'ı, K8s manifest'lerinin küçük kardeşi; kavramlar (service, volume, depends_on) birebir taşınır

<Callout type="warn" title="Compose production için değildir (genelde)">
  Compose tek makinede konuşur; çoğul sunucu, otomatik yeniden planlama, rolling update
  gibi konular orkestratör (Kubernetes) işidir. Compose’u geliştirme/test ortamının
  standardı olarak düşün.
</Callout>
