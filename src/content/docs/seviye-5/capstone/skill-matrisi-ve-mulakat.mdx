Bu reponun seviyelerini sektörel beklentiye çevirirsek:

| Beceri alanı | Junior | Mid | Senior |
| --- | --- | --- | --- |
| **Linux/Ağ** | Temel komutlar, SSH, servis yönetimi | Perf analizi, ağ diagnoz | Kernel/resource tuning, güvenli ağ mimarisi |

## Sık mülakat soruları ve cevap iskeletleri

### 1. “CI/CD pipeline'ını nasıl tasarlarsın?”

İskelet: **kalite kapıları** (lint→test→scan→build) → **artifact tek üretim** (imaj, sha tag) → **ortam katmanları** (staging otomatik, prod onaylı/canary) → **gölge konular** (cache, secrets, rollback). Capstone akışını anlat — kendi kurdugun sistemin hikâyesi, ezberden bin kat güçlüdür.

### 2. “Bir deployment sonrası hata oranına %20 arttı. Ne yaparsın?”

İskelet: **mitigate-first** (rollback/flag — etkilenen müşteri süresini kısalt) → **ölçümle doğrula** (canary %'si, error rate metrikleri) → **kök neden** (trace + log) → **postmortem + aksiyon** (tekrarı kapat). Sıralama önemli: önce etkiyi kes.

### 3. “Error budget nedir, neden %100 hedeflenmez?”

İskelet: SLO %99.5 → bütçe = izin verilen başarısızlık → risk sermayesi → tükendiğinde feature durur, reliability işi önceliklenir → %100 hedefi geliştirmeyi felç eder ve kullanıcıya duyulmaz fark üretir.

### 4. “GitOps nedir, push modelinden farkı?”

İskelet: Git = istenen hâl → operator (ArgoCD/Flux) sürekli eşitler → drift detection → **pull güvenliği** (kümeye dış yazma kimliği yok) → audit/rollback = git log/revert.

### 5. “Container içindeki süreç neden PID 1 özel?”

İskelet: container'ın ana süreci (ENTRYPOINT) PID 1 — ölürse container ölür → signal handling önemi (SIGTERM'e düzgün yanıt = graceful shutdown) → zombie süreç sorumluluğu → health check entegrasyonu.

### 6. “Sistem yavaşladı, nereden başlarsın?”

İskelet: kullanıcı perspektifinden daralt (Seviye 1 diagnoz akışı) → metriklerle lokasyon (p99 hangi serviste — trace) → kaynak doygunluğu (CPU/mem/IO/net) → son kod değişikliği (`git log`) → kök neden + ölçümle doğrulama.

<Callout type="tip" title="Cevap formülü">
  Her soruda: (1) kısa tanım → (2) neden önemli → (3) kendi deneyiminden somut örnek
  → (4) trade-off’lar. “Trade-off” kelimesi senior sinyalidir: her kararı bir bedeliyle
  anlatmak, ezberi taklitten ayıran çizgidir.
</Callout>

## Yolculuktan sonraki yollar

Bu reponun 5 seviyesi = sağlam **mid-level DevOps zemini**. Büyüme yolları:

1. **Derinleşme:** Kubernetes (CKA/CKAD sertifikaları), cloud sertifikaları (AWS SA/Azure dev), security (CKS)
2. **Genişleme:** veritabanı operasyonları, message broker'lar (Kafka/RabbitMQ), service mesh (Istio)
3. **Platform yolu:** Backstage, IDP tasarımı, DX ölçümleri (Seviye 5 platform dersi)
4. **SRE yolu:** Google SRE kitapları (ücretsiz!), SLO programı kurma, incident komutanlığı pratiği
5. **Topluluk:** açık kaynak katkısı (dokümantasyon iyi başlangıç), kendi araçlarını yayınlama — bu repo gibi!

## Son söz

DevOps'un özeti üç cümlede:

- **Kültür:** sen yaz, sen çalıştır; hatayı saklama, sistemden öğren.
- **Pratik:** küçük parçalar, otomatik kapılar, ölçülebilir güvenilirlik.
- **Araç:** konuya hizmet eder — “araç kültürü çözmez.”

Bu repo boyunca tek bir projeyi (bu sitenin kendisini) seviye seviye üretimsel olgunluğa taşıdın. Bundan sonrası: **kendi projelerinde tekrarla.** İyi yolculuklar! 🚀
