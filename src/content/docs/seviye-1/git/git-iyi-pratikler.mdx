## Commit mesajı neden standart olsun?

“fix”, “düzenleme”, “asdasd” — üç ay sonra kimse ne demek istendiğini hatırlamaz. Standart commit mesajı:

1. **changelog otomatikleştirir** (Seviye 5'te release otomasyonunda kullanacağız)
2. **sürüm numarasını belirler** (hangi commit “major” tetikler?)
3. **geçmişi aranabilir yapar** (“tüm breaking change'leri listele”)

## Conventional Commits formatı

```
<tip>(<kapsam>): <kısa özet>

<opsiyonel gövde>

<opsiyonel footer: BREAKING CHANGE vb.>
```

Tip seti:

| Tip | Ne zaman? |
| --- | --- |
| `feat` | Yeni özellik |
| `fix` | Hata düzeltmesi |
| `docs` | Dokümantasyon |
| `refactor` | Davranış değişmeyen yapısal iyileştirme |
| `test` | Test ekleme/düzeltme |
| `chore` | Yapılandırma, bağımlılık, araç |
| `ci` | CI pipeline değişikliği |

```bash
feat(auth): Google ile giriş desteği
fix(api): 500 hatasına yol açan null kontrol eksikliği
chore!: Node 22 zorunluluğu   # ünlem = BREAKING CHANGE
```

## Semantic Versioning (Semver)

Sürüm numarası: **MAJOR.MINOR.PATCH** (`v2.4.1`)

| Artar | Ne zaman | Örnek |
| --- | --- | --- |
| **MAJOR** | Uyumluluğu kıran değişiklik | API'den parametre kaldırma |
| **MINOR** | Geriye uyumlu yeni özellik | Yeni endpoint |
| **PATCH** | Geriye uyumlu hata düzeltme | Crash fix'i |

Conventional Commits + Semver kombinasyonu otomasyona dönüşür: `feat` commit'i MINOR artırır, `fix` PATCH, `BREAKING CHANGE` MAJOR. `semantic-release` gibi araçlar bunu uçtan uca yapar.

<Callout type="tip" title="Mülakat klasiği">
  “v2.10.0 ile v2.2.0’ı karşılaştır” — metin olarak yanlış (10 < 2), Semver olarak doğru
  (10 > 2). Sürüm karşılaştırmaları metin değil, sayı üçlüsü üzerinden yapılır.
</Callout>

## Git hooks: commit anında kalite kapısı

`.git/hooks/` altındaki scriptler Git olaylarında otomatik çalışır. En çok kullanılanlar:

- **pre-commit:** commit öncesi kontrol (lint, format, büyük dosya engeli)
- **commit-msg:** mesaj formatı doğrulama
- **pre-push:** push öncesi test

Basit bir pre-commit örneği:

```bash
#!/usr/bin/env bash
# .git/hooks/pre-commit — build çıktısını repoya engelle
if git diff --cached --name-only | grep -q "^dist/"; then
  echo "❌ dist/ dosyaları commit edilemez (build çıktısı!)"
  exit 1
fi
```

Tek kişi için yeterli ama ekipte sorun: hooks `.git/` klasöründe olduğu için **versiyonlanmaz**. Çözüm: [husky](https://typicode.github.io/husky/) gibi araçlar hook'ları repoda yönetir (Seviye 2'de CI'a bağlayacağız).
