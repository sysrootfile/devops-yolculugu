## Süreç: çalışan her şey

Program diskte **dosya**dır; çalışmaya başladığında **süreç (process)** olur ve bir PID (process ID) alır. DevOps’un “sunucuda ne oluyor?” sorusunun ilk cevabı süreç listesidir:

```bash
ps aux                    # tüm süreçler
ps aux | grep nginx       # nginx süreçlerini filtrele
top                       # canlı görünüm (çıkış: q)
kill 1234                 # 1234 numaralı süreci nazikçe bitir (SIGTERM)
kill -9 1234              # zorla bitir (SIGKILL — son çare)
```

`ps aux` çıktısında bakılacak kolonlar: **%CPU, %MEM** (kaynak tüketimi) ve **STAT** (R=çalışıyor, S=uyuyor, Z=zombi).

## systemd: sunucunun orkestra şefi

Modern Linux dağıtımlarında servisleri **systemd** yönetir. Her servis bir “unit” dosyasıdır (`/etc/systemd/system/*.service`). DevOps için bilmen gereken komut seti şunlar:

```bash
sudo systemctl start nginx      # başlat
sudo systemctl stop nginx       # durdur
sudo systemctl restart nginx    # yeniden başlat
sudo systemctl status nginx     # durum + son loglar
sudo systemctl enable nginx     # açılışta otomatik başlasın
sudo systemctl disable nginx    # otomatik başlatmayı kapat
systemctl list-units --type=service --state=running   # çalışan servisler
```

`enable` ile `start` farkı klasik sorudur: **start** şimdi başlatır, **enable** reboot sonrası de başlatır. Production'da ikisi de istenir.

## Loglar: olaydan sonra gerçeği söyleyen tek şey

systemd'nin log servisi **journald**, tüm servis loglarını ikili formatta tutar:

```bash
journalctl -u nginx               # nginx servis logları
journalctl -u nginx -f            # canlı takip (tail -f gibi; çıkış: Ctrl+C)
journalctl -u nginx --since "1 hour ago"
journalctl -p err -b              # bu açılıştan beri hata seviyesindekiler
journalctl --disk-usage           # logların ne kadar yer tuttuğu
```

Klasik olmayan (kendi dosyasına yazan) uygulamalar için:

```bash
tail -f /var/log/app/app.log      # dosya logunu canlı izle
tail -100 /var/log/syslog         # son 100 satır
```

<Callout type="tip" title="Sorun giderme akışı (ezberele)">
  1) `systemctl status <servis>` → 2) çalışmıyorsa `journalctl -u <servis> -n 50` →
  3) hata satırını oku → 4) yapılandırma mı, kaynak mı (bellek/disk/port), bağımlılık mı?
  Bu akış, karşılaşacağın olayların %80’ini çözer.
</Callout>

## Süreç yönetiminin DevOps bağlantısı

- **Monitoring** (Seviye 4) aslında `ps`/`top`un sürekli ve otomatik halidir.
- **Container'lar** süreç yönetimini değiştirir: her container tek ana süreçle çalışır; PID 1 container'ın yaşamıdır.
- **systemd unit dosyası** yazmak, kendi uygulamanı “sunucu servisi” yapmanın klasik yoludur — IaC (Seviye 3) bu tanımları kodlaştırır.
