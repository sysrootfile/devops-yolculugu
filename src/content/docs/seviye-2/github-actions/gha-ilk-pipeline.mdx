## Bu derste ne yapacağız?

Seviye 0'da söz vermiştik: bu site kendi altyapısı üzerinde öğretilecek. Şimdi sıra **kendi CI'ını yazmakta**. Repo'yu GitHub'a gönderdiğinde her push ve PR'da otomatik olarak:

1. Bağımlılıklar kurulacak
2. Site derlenecek (bu, içerik şeması kontrolü demek!)
3. Üretilen HTML içinde temel kontroller yapılacak

## Workflow dosyası

`.github/workflows/ci.yml` dosyasını oluştur:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Repoyu indir
        uses: actions/checkout@v5

      - name: Node kur
        uses: actions/setup-node@v5
        with:
          node-version: 22
          cache: npm

      - name: Bağımlılıkları kur
        run: npm ci

      - name: Siteyi derle
        run: npm run build

      - name: Üretilen sayfaları doğrula
        run: |
          test -d dist || { echo "dist/ yok!"; exit 1; }
          test -f dist/index.html || { echo "ana sayfa üretilmemiş!"; exit 1; }
          echo "✅ $(find dist -name 'index.html' | wc -l) sayfa üretildi"
```

Son step'te çok satırlı bir script görüyorsun (`run: |`): her satır ayrı bir kabuk komutudur ve `exit 1` ile pipeline'ı bilinçli kırmızıya çevirebilirsin — **kontrolün kendisi de kod**.

## Ne oldu burada? (adım adım)

1. `checkout` — runner boş makinedir; repoyu indirir
2. `setup-node` + `cache: npm` — Node 22 kurar, npm cache'i (bir sonraki derste detay) bağlar
3. `npm ci` — lockfile'a sadık temiz kurulum
4. `npm run build` — Astro derler. **Bu step aslında testtir:** geçersiz frontmatter, bozuk MDX import'u veya eksik bileşen varsa build kırmızı olur
5. Doğrulama — `dist/` içinde index.html var mı, kaç sayfa üretildi?

## GitHub'a bağlama

<LabBox
  id="s2-gha-lab"
  title="CI'ı canlıya taşı"
  verify={['git log --oneline -3', 'git remote -v']}
>
  1. Bu repoyu GitHub'da bir depoya gönder (önceki seviyenin lab'ında remote tanımlamıştın; yoksa GitHub'da boş repo aç → `git remote add origin ...` → `git push -u origin main`).
  2. `.github/workflows/ci.yml` dosyasını yukarıdaki içerikle oluştur ve commit'le: `ci: ilk pipeline` (Conventional Commits — bir önceki seviye!).
  3. GitHub'da **Actions** sekmesine gir: koşum listesini gör.
  4. Bir derse bilerek bozuk bir şey ekle (ör. bir MDX dosyasında `level: 9`), push et — pipeline'ın **kırmızı** olduğunu ve hatanın logunda göründüğünü izle.
  5. Hatayı düzelt, push et — yeşil. **Tebrikler: içerik kalitesi artık CI kontrolünde.**

  Not: Public repolarda GitHub Actions ücretsizdir.
</LabBox>

<Callout type="info" title="Log okuma pratiği">
  Kırmızı bir job’da tıklanacak sıra: hangi step kırmızı? → o step’in son 20 satırı →
  en alttaki ilk hata satırı. Loglar uzundur ama hatanın kendisi hep diptedir; “render
  hatası: invalid frontmatter at seviye-3/docker/x.mdx” gibi bir satır, tam dosyayı ve
  satırı işaret eder.
</Callout>

<Callout type="info" title="Gerçek dünyadan: bu reponun kendi CI'ında yaşandı">
  Bu siteye kurduğumuz pipeline'da GitHub bir gün şu annotation'ı düşürdü:
  “actions/checkout@v4, Node.js 20 deprecated...” — yani bağımlılık değil,
  **pipeline'ın kendi bileşenleri de eskir ve bakım ister**. Repoyu v5'e yükseltip
  ders örneklerini senkronladık. Çıkarım: CI, kurulup unutulacak bir şey değil;
  kendisi de versiyonlanan, bakılan bir üründür (dogfooding'in ikinci dersi!).
</Callout>

## Bundan sonrası

Pipeline artık her değişikliği doğruluyor. Sırada iki güçlendirme var: **secrets** (bir sonraki ders — deploy kimlik bilgileri) ve **cache/artifact** (dersten sonra — hız). Seviye 3'te bu pipeline'ın sonuna Docker imajı üretimini ekleyeceğiz.
