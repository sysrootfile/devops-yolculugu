## Secret nedir, neden repoya yazılmaz?

Deploy etmek için bir yerde kimlik belgelemek gerekir: deploy token'ı, API anahtarı, sunucu şifresi. Bunlar **secret**'tır. Repoya yazılırsa:

1. Repo public ise anında sızar (botlar saniyeler içinde tarar)
2. Repo private olsa bile **git geçmişinde kalır** — silsen bile eski commit'lerde durur
3. Tüm PR sahipleri ve fork'lar risk altına girer

Çözüm: secret'lar GitHub'ın **şifreli deposunda** tutulur, workflow'a yalnızca çalışma anında, **maskelenmiş** olarak verilir.

## Secrets'ı kullanmak

Repo → **Settings → Secrets and variables → Actions → New repository secret** ile eklenir. Workflow'da:

```yaml
steps:
  - name: Deploy
    run: ./deploy.sh
    env:
      DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}   # sıradan env değişkeni gibi
```

Kritik davranışlar:

- Loglarda `***` olarak maskelenir
- Fork'tan gelen PR'lar secret'lara **erişemez** (varsayılan)
- Secret'ı `echo $DEPLOY_TOKEN` ile yazdırsan bile GitHub maskeler — ama bilerek kullanma, bypass yöntemleri (base64 vb.) maskelenebilir ve saldırı yüzeyi açar

<Callout type="tip" title="En az yetki secret’ta da geçerli">
  Deployscope’u tüm reponun anahtarını veren `admin` token’ı değil, yalnızca deploy
  yetkisi olan dar kapsamlı (scoped) bir token kullan. Token’ın ömrü kısa olsun;
  rotasyon politikası Seviye 4’te secret yönetimi dersinde derinleşecek.
</Callout>

## Environments: prod için ek kapı

**Environment** (ortam), job'lar için güvenlik paketidir: koruma kuralları + izole secret'lar.

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: production        # korumalı ortam
      url: https://devops-yolculugu.example.com
    steps:
      - uses: actions/checkout@v4
      - run: ./deploy.sh
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}   # production env'inin secret'ı
```

`production` environment'ında ayarlanabilecekler:

- **Required reviewers:** deploy öncesi belirli kişilerin onayı (Continuous Delivery'in CI karşılığı!)
- **Branch restriction:** yalnızca `main`den deploy
- **İzole secret'lar:** `production` env'inin `DEPLOY_TOKEN`'ı ile `staging`'ininkiler farklıdır

Bu model, “aynı workflow dosyası, farklı güvenlik katmanı” deseni sağlar: staging otomatik, prod onaylı.

## Sızan secret'ta ne yapılır? (olay planı)

1. **Geri al (revoke):** token'ı hemen geçersizleştir — “geçmişi temizlemek” yeterli değildir
2. **Yeni secret üret ve değiştir**
3. **Geçmişte nereye sızmış tarayıp** (git log, `git grep`) erişim izlerini kontrol et
4. **Olay kaydı:** ne oldu, ne zaman, nasıl — postmortem'e hazırla (Seviye 4)
5. **Kök neden:** gitignore eksik mi, review atlanmış mı? Süreci düzelt

“Geçmişten silmek” (`git filter-repo`, force push) **tamamlayıcı**dır ama asıl güvenlik revoke'tur: geçmişi klonlamış biri olabilir.

## Variables vs Secrets

| | `vars.X` | `secrets.X` |
| --- | --- | --- |
| Amaç | Yapılandırma değeri (URL, flag) | Kimlik bilgisi |
| Logda | Görünür | Maskelenir |
| Örnek | `SITE_URL=prod.example.com` | `DEPLOY_TOKEN` |

Gizli olmayan her şey `vars`/`env` olabilir — secret'ı sadece gerçekten gizliye saklamanın faydası, maskemezi anlamlı kalmasıdır.
