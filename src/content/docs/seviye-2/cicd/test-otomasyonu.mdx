## Test piramidi: denge sanatı

Test tipleri maliyet ve hız açısından bir piramit oluşturur:

```
        /  E2E  \        ← yavaş, kırılgan, pahalı (az tutulur)
       / Integration \    ← orta hız, sınırlar arası davranış
      /     Unit      \   ← hızlı, ucuz, binlerce olabilir (çoğunluk)
```

| Katman | Neyi korur? | Süre | Kırılganlık |
| --- | --- | --- | --- |
| **Unit** | Tek fonksiyonun doğru davranışı | ms | Düşük |
| **Integration** | Bileşenlerin birlikte çalışması (DB, API...) | sn–dk | Orta |
| **E2E** | Gerçek tarayıcıda kullanıcı yolculuğu | dk | Yüksek |

<Callout type="warn" title="Dondurulmuş dondurbaç (ice cream cone) antipattern’i">
  Piramit tersine dönerse — çoğu test E2E — pipeline yavaşlar, testler rastgele kırılır
  (flaky), ekib testlere güvenini kaybeder ve “test kırmızıysa da merge edelim” kültürü
  doğar. Güven kaybolan test süitinin çıktısı gürültüdür, koruma değil.
</Callout>

## Bu siteyi test ederken ne koruruz?

Bu Astro projesi üzerinden somutlaştıralım — Seviye 0'daki “dogfooding” işte burada:

**1. Unit test — içerik şeması:**

Astro'nun Content Collections, `level: 7` gibi geçersiz veriyi build anında reddeder. Bu aslında şema tabanlı bir testtir. Ek olarak kendi kontrollerini yazabilirsin — ve **bu repoda gerçekten yazıldı**: `scripts/validate-content.mjs`

```bash
npm test   # çalıştır: 53 ders + tüm interaktif bileşen id'leri doğrulanır
```

Script'in kontrol ettiği şeyler (tam listesi dosyanın başında): ders id'lerinin benzersizliği, aynı (seviye, modül) içinde order çakışması olmaması, `prerequisites` referanslarının gerçek derslere işaret etmesi, quiz/lab/terminal bileşenlerinde `id="..."` çakışması olmaması. CI'da build'den **önce** ayrı bir adım olarak koşar — test, build'den hızlıdır ve kırılganlığı erken yakalar.

**2. Integration test — derleme:**

```bash
npm run build   # başarısız MDX, bozuk import, eksik bileşen = kırmızı
```

“Build geçti” ifadesi bu projedeki en güçlü integration testidir: tüm sayfaların statik olarak üretilmesi, tüm iç linklerin çözülmesi demektir.

**3. E2E test — kullanıcı yolculuğu:**

Playwright ile: “ana sayfayı aç → Seviye 1'e tıkla → quiz cevapla → doğru skor kaydedildi mi?” Bu test, tarayıcıdaki interaktif bileşenlerin (quiz, terminal) gerçekten çalıştığını doğrular.

<Callout type="info" title="Gerçek dünyadan (bu repo): E2E katmanı da canlı">
  Hayali örnek kalmadı — bu repoda `tests/e2e/site.spec.ts` altında 6 Playwright
  testi koşuyor: dashboard yüklemesi, quiz cevaplama, tema kalıcılığı, arama,
  terminal simülatörü, tamamlama butonu. CI'da bunlar **ayrı bir `e2e` job'ıdır**
  (build → e2e → docker → deploy). Ve ilk koşumunun meyvesi: arama sonuç
  panelinin DOM'da var olup **hiç görünmediği** bir CSS bug'ını yakaladı —
  DOM-level testler göremezdi, E2E görünürlüğü doğruladı. Piramidin katmanları
  farklı şeyleri korur; biri diğerinin yerine geçmez.
</Callout>

## Hangi değişiklik hangi testi tetikler?

Ekipte “test stratejisi” diyince konuşulan tablodur:

| Değişiklik | Tetiklenmesi gereken |
| --- | --- |
| `components/Quiz.astro` | Unit (varsa) + E2E quiz senaryosu |
| İçerik (.mdx) | Build + link kontrolü |
| `styles/global.css` | Görsel smoke test (klasik E2E yeterli) |
| `package.json` bağımlılığı | Tam süit + güvenlik taraması |

## Testler pipeline'da nasıl koşar?

```yaml
# Yakında yazacağımız CI'ın iskeleti
steps:
  - run: npm ci            # temiz kurulum
  - run: npm run build     # integration katmanı
  - run: npx playwright test   # E2E (paralel, container içinde)
```

İki kural:

1. **PR'da hızlı süit** koşar (unit + build) — geliştirici beklemesin
2. **Merge sonrası tam süit** koşar (E2E dahil) — main her zaman kanıtlı olsun

<Callout type="info" title="Gerçek dünyadan: Google'ın flaky test savaşı">
  Google, 2016'da yayınladığı deneyim yazısında milyonlarca test koşumunda
  flakiness'ın **kaçınılmaz** olduğunu söyledi: çözüm silmek değil, flaky testleri
  otomatik tespit edip izole kanallara ayırmak ve sahiplerine ölçülebilir SLA ile
  düzelttirmekti. Yani “flaky = gürültü” sorunu, büyük ölçekte bir **mühendislik
  programıdır** — bu dersin uyarısının endüstriyel versiyonu.
</Callout>

## Flaky test: güven düşmanı

Her koşumda aynı sonucu vermeyen test (flaky) ekipti iki şekilde zehirler: kırmızıya alışma ve sahte yeşillere itimat. Tavsiyeler: önce flakiness'ın kökünü bul (async bekleme, paylaşılan veritabanı durumu...), düzeltemiyorsan testi **gürültü kanalına** ayır ama silme — ve kesinlikle diğer testlerin sonucunu çarpıtmasına izin verme.
